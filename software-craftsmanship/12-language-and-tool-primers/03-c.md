## Key Takeaways

- **Memory is a sequence of bytes with numeric addresses.** A C pointer is one of those addresses plus the type of what lives there, and `p[i]` is the object `i * sizeof(*p)` bytes past `p`.
- **C checks nothing at run time.** An index past the end, a freed pointer, or a signed overflow is undefined behavior: no exception, just wrong bytes. AddressSanitizer and UndefinedBehaviorSanitizer turn most of it into a crash with a report, so you build and test with them on.
- **`realloc` may move the buffer and may fail.** Keep the old pointer until it succeeds, and grow geometrically (double), or pushing n elements costs O(n²).
- **A struct has padding.** Each field starts at a multiple of its alignment, so `{int32_t id; double score;}` is 16 bytes with `score` at offset 8, and Python must mirror that layout field for field.
- **ctypes knows nothing about your header.** Undeclared functions take and return C `int`, which silently truncates 64-bit values. Declare `argtypes` and `restype` for every function you call.

## 1. Why now

Your system has no C in it yet. The next module, `rt.01`, writes its first C file and the Python loader that calls into it; the one after, `M03.1`, writes a matrix multiply that reads two matrices through raw `float *` pointers and that your bigram model (`L0.0`) and your Rust engine (`L10.0`) both call. In Python, `a[7]` on a 6-element list raises `IndexError`. In C, `A[7]` on a 6-element array reads whatever 4 bytes happen to follow it, quietly, and the matmul returns a plausible number that is wrong. Python frees memory for you; in C, a buffer you forget to free leaks for the life of the engine, and one you free twice corrupts the allocator for a crash an hour later somewhere else. This primer gives you the model of memory that C assumes, the tools that catch its failures (sanitizers), and the one bridge your Python uses to reach C (ctypes), on two exercises small enough to reason about completely.

## 2. Principles

Notation used in this chapter:

| Symbol | Meaning | Type / shape |
|---|---|---|

| `_Alignof(T)` | `T`'s alignment: its address must be a multiple of this | `size_t`, a power of two |
| `&x` | the address of object `x` | `T *` |
| `*p` | the object at address `p` | `T` |

| `p[i]` | the same as `*(p + i)` | `T` |
| `offsetof(S, f)` | bytes from the start of struct `S` to its field `f` | `size_t` |
| $\mathrm{roundup}(x, a)$ | the smallest multiple of $a$ that is $\ge x$: $\lfloor (x + a - 1) / a \rfloor \cdot a$ | integer |
| $n$, $\mathit{len}$, $\mathit{cap}$ | element counts in section 2.4 and 3 | `size_t` |

### 2.1 Bytes, addresses, and types

Memory, as a C program sees it, is one long array of bytes. Each byte has an **address**, an integer (on a 64-bit machine, 64 bits wide). A C **object** is a run of consecutive bytes, and its **type** says how many and how to read them:

| Type | `sizeof` on a 64-bit Mac or Linux | Holds |
|---|---|---|
| `char`, `int8_t`, `uint8_t` | 1 | a byte |
| `int32_t`, `uint32_t`, `float` | 4 | a 32-bit integer; a 32-bit IEEE 754 float |
| `int64_t`, `uint64_t`, `double` | 8 | a 64-bit integer; a 64-bit float |
| `int` | 4 (the standard only promises at least 2) | the "natural" integer |
| `size_t` | 8 | a size or an index; unsigned, so `0 - 1` wraps to the largest value |
| any pointer `T *` | 8 | an address |

Use the fixed-width types from `<stdint.h>` (`int32_t`, `int64_t`) whenever the width matters, which is always at a language boundary: Python and Rust must agree with C on every byte.

### 2.2 Pointers and pointer arithmetic

A **pointer** `T *p` holds an address and remembers the type at that address. `&x` takes the address of `x`; `*p` is the object at `p`. **NULL** is the address no object has; dereferencing it is an error. Arithmetic on a pointer counts in elements, not bytes: if `p` points at an `int32_t` at address 4096, `p + 3` is 4096 + 3 · 4 = 4108. Indexing is defined as arithmetic: `p[i]` means `*(p + i)`.

An **array** `int32_t xs[5]` is 5 objects back to back, 20 bytes. In almost every expression the array's name **decays** to a pointer to its first element, which is why a function that takes `const int32_t *xs` can receive an array, and why it must also receive the length separately: the pointer does not carry it. `const T *p` promises the function will not write through `p`; the compiler holds you to it.

A matrix is stored the same way, as one flat run of numbers. Row-major order puts row 0 first, then row 1, so element $(i, k)$ of an $M \times K$ matrix is `A[i * K + k]`. `M03.1` builds on exactly this.

### 2.3 Structs, alignment, and padding

A **struct** groups fields into one object. The hardware reads an 8-byte `double` fastest (on some machines, only) at an address that is a multiple of 8, so every type has an **alignment**, and the compiler places each field at the next offset that is a multiple of the field's alignment:

$$\mathrm{offset}_k = \mathrm{roundup}(\mathrm{offset}_{k-1} + \mathrm{sizeof}(\mathrm{field}_{k-1}),\ \mathrm{alignof}(\mathrm{field}_k)), \qquad \mathrm{offset}_0 = 0$$

The unused bytes between fields are **padding**. The struct's own alignment is its largest field alignment, and its size is rounded up to a multiple of that, so that in an array of structs every element's fields stay aligned. The compiler never reorders fields. Section 3 works one layout by hand.

### 2.4 Where objects live: stack, static, heap

| Storage | How you get it | Lifetime |
|---|---|---|
| automatic ("the stack") | a local variable `float x[4];` | until the function returns; a pointer to it afterwards dangles |
| static | a variable at file scope, or `static` inside a function | the whole program |
| allocated ("the heap") | `malloc(n)`, `calloc(k, n)`, `realloc(p, n)` | until you `free(p)` |

`malloc(n)` returns a pointer to `n` fresh, uninitialized bytes, or NULL when it cannot. `free(p)` gives them back; `free(NULL)` does nothing. **Ownership** is the rule you keep in your head: exactly one piece of code is responsible for freeing each block, exactly once.

`realloc(p, n)` resizes the block at `p` to `n` bytes. It may grow it in place, or allocate a new block, copy the old bytes, free the old block, and return the new address: **every pointer into the old block is then dangling**. If it fails it returns NULL and leaves the old block untouched and still yours. `realloc(NULL, n)` is `malloc(n)`. `realloc(p, 0)` is implementation-defined in C11 and undefined in C23: do not use it.

A growable array keeps $\mathit{len}$ elements in a buffer of capacity $\mathit{cap} \ge \mathit{len}$. When a push finds $\mathit{len} = \mathit{cap}$ it must grow. Growing by a constant $c$ copies $\mathit{len}$ elements every $c$ pushes, about $n^2 / (2c)$ copies for $n$ pushes. Growing by a factor $g > 1$ (doubling, $g = 2$) copies at most $n (1 + 1/g + 1/g^2 + \dots) = n \cdot g / (g - 1)$ elements in total, a constant amount per push on average (**amortized O(1)**).

### 2.5 Undefined behavior and the sanitizers

The C standard lists operations whose result is **undefined**: reading or writing outside an object, using memory after `free`, freeing twice, dereferencing NULL, reading an uninitialized variable, overflowing a **signed** integer (`int32_t` 2,000,000,000 + 2,000,000,000), shifting by the width or more. "Undefined" does not mean "crashes". The compiler optimizes on the assumption that it never happens, so the program may appear to work, return a wrong number, or fail somewhere far away. Unsigned arithmetic (`size_t`, `uint32_t`) is defined: it wraps around modulo $2^{w}$.

Two compiler-inserted checkers find most of it at run time:

| Flag | Name | Catches |
|---|---|---|
| `-fsanitize=address` | AddressSanitizer (ASan) | out-of-bounds reads and writes on heap, stack, and globals; use after free; double free. It surrounds every block with poisoned "redzones" and keeps freed memory poisoned for a while |
| `-fsanitize=undefined` | UndefinedBehaviorSanitizer (UBSan) | signed overflow, misaligned pointers, NULL dereference, bad shifts, out-of-range conversions |
| `-fno-sanitize-recover=undefined` | | make UBSan stop the program at the first report instead of printing and continuing |

Apple's clang has no LeakSanitizer (the Linux leak checker), so the course detects leaks by **counting** allocations: the test routes your `malloc`, `realloc`, and `free` through wrappers that keep a live-block count and fails any test that ends above zero. `rt.01` makes that a design rule of the whole C library (the allocator hook).

### 2.6 Headers, declarations, and linkage

`lang.02` showed the two build stages: compile each `.c` to an object file, then link the objects. What crosses between files is **names**:

- A **declaration** says a name exists and what its type is: `int vec_push(Vec *v, int x);`. A **definition** creates it: the function with its body, or a variable with its storage. A name may be declared many times and defined once.
- A **header** is a file of declarations that every `.c` using them `#include`s. The preprocessor pastes it in textually, so a header is protected by an **include guard** (`#ifndef VEC_H` / `#define VEC_H` / `#endif`) against being pasted twice into one file.
- **Linkage** decides who can see a name. A function or file-scope variable has **external** linkage by default: its name is exported from the object file as a **symbol**, and the linker resolves every other file's use of it. Marked `static`, it has **internal** linkage: visible only inside its own file, and no symbol is exported.

`nm file.o` lists an object's symbols: `T` for a function defined here, `U` for one used here but defined elsewhere. On macOS every C symbol carries a leading underscore (`_vec_push`). A **shared library** (`.dylib` on macOS, `.so` on Linux) is a linked file that a running program loads later with `dlopen` and searches by symbol name with `dlsym`. All the libraries in one process share one namespace of symbol names, which is why every exported name in your C library will carry the prefix `tl_` and every helper will be `static` (`rt.01`).

### 2.8 Calling C from Python with ctypes

`ctypes` is Python's built-in bridge to shared libraries. `lib = ctypes.CDLL(path)` calls `dlopen`; `lib.rt_sum_i32` calls `dlsym` and returns a callable. ctypes cannot read your header, so **you** tell it each function's types:

```python
lib.rt_sum_i32.argtypes = [ctypes.POINTER(ctypes.c_int32), ctypes.c_size_t]
lib.rt_sum_i32.restype = ctypes.c_int64
```

Without them, ctypes guesses: every argument and the return value are C `int` (32 bits). A 64-bit return comes back with its top half cut off, a pointer argument may be truncated, and nothing reports an error. The type names map one to one: `c_int32`, `c_int64`, `c_size_t`, `c_float`, `c_double`, `POINTER(T)` for `T *`, `None` as a restype for `void`. `(ctypes.c_int32 * n)(*xs)` builds a C array of `n` int32 values from a Python list, and passing it where a pointer is expected passes its address. A `ctypes.Structure` subclass with a `_fields_` list mirrors a C struct; ctypes applies the same alignment rule as the C compiler (2.3), so the layouts agree exactly when the fields are listed in the same order with the same types. `ctypes.byref(obj)` passes `&obj`.

What crosses the boundary: **values** (ints, floats) are copied; **pointers** share memory, so C's writes through a pointer are visible to Python after the call. Python's garbage collector does not know C holds a pointer: keep the Python object alive for as long as C may use the address.

One more rule from the toolchain: a library built with AddressSanitizer cannot be loaded into a Python that was not itself built with it (on macOS the ASan runtime must be loaded first). The check therefore tests `vec.c` in a standalone ASan test program, and builds `roundtrip.c` with UBSan only, which does load into Python.

## 3. Worked example by hand

**Growing a vector.** Start from `vec_init` ($\mathit{len} = \mathit{cap} = 0$, `data == NULL`) and push 10, 20, 30, 40, 50, doubling from a first capacity of 4:

| Push | $\mathit{len}$ before | $\mathit{cap}$ before | Grows? | Call | $\mathit{cap}$ after | Buffer bytes |
|---|---|---|---|---|---|---|
| 10 | 0 | 0 | yes | `realloc(NULL, 16)` (a malloc) | 4 | 16 |
| 20 | 1 | 4 | no | | 4 | 16 |
| 30 | 2 | 4 | no | | 4 | 16 |
| 40 | 3 | 4 | no | | 4 | 16 |
| 50 | 4 | 4 | yes | `realloc(data, 32)`: may move, copies 16 bytes | 8 | 32 |

After three pushes, `vec_get(&v, 1)` reads `*(data + 1)`, the 4 bytes at `data + 4`: 20. This is the first test, `push_and_get_by_hand`. If `realloc` at push 50 had failed, it would return NULL with the 16-byte block still holding 10, 20, 30, 40, which is why the old pointer must survive the call.

**Laying out a struct.** `rt_pair` in `roundtrip.h` is `{int32_t id; double score;}`:

| Field | sizeof | alignof | Offset | Why |
|---|---|---|---|---|
| `id` | 4 | 4 | 0 | the first field starts at 0 |
| (padding) | 4 | | 4 to 7 | `score` needs a multiple of 8 |
| `score` | 8 | 8 | 8 | $\mathrm{roundup}(0 + 4, 8) = 8$ |
| struct | **16** | 8 | | ends at 16, already a multiple of 8 |

In an array `rt_pair ps[3]`, element 2's `score` is at $2 \cdot 16 + 8 = 40$ bytes from `ps`. Swap the field order in Python's `_fields_` and ctypes computes `score` at offset 0 and `id` at 8: every value C writes is read back from the wrong bytes. `test_struct_layout_matches_c` checks exactly these numbers: 16 and 8.

**A round trip.** `sum_i32(lib, [1, 2, 3])`: Python builds a 12-byte C array holding 1, 2, 3 and passes its address and the length 3; C adds into an `int64_t` and returns 6 in a 64-bit register; ctypes reads it as `c_int64` and hands Python the int 6. With `[2000000000, 2000000000]` the sum is 4,000,000,000, which needs 33 bits: adding in `int32_t` inside C is a signed overflow (UBSan stops it), and returning through an undeclared restype cuts it to 32 bits, -294,967,296.

## 5. Pitfalls

| Pitfall | Symptom | Caught by |
|---|---|---|
| `v->data = realloc(v->data, ...)` | when `realloc` fails, the only pointer to the old buffer is lost: the elements are gone and the block leaks | `failed_growth_leaves_the_vec_unchanged` |
| growing by one (or any constant) | correct but quadratic: a million pushes take seconds | `growth_is_geometric` |
| `vec_pop` reading `data[len - 1]` without checking `len` | `len - 1` on a `size_t` 0 wraps to $2^{64} - 1$; ASan reports a wild read | `pop_is_lifo` |
| `vec_free` leaving `data` set | the second call frees the same block twice | `free_is_idempotent` |
| no `restype` on a function returning `int64_t` | large results come back negative, no error | `test_sum_needs_the_declared_restype`, `test_load_declares_the_c_types` |
| summing `int32_t` values in an `int32_t` | signed overflow: undefined behavior that UBSan stops | `test_sum_needs_the_declared_restype` |
| `_fields_` in a different order than the C struct | every field after the first reads garbage | `test_struct_layout_matches_c` |
| `>=` when comparing scores | ties pick the last index instead of the first | `test_best_pair_fills_an_out_parameter` |

## L8.3: paged-cache mutants target the Python block store

After removing the native KV pool, the axis-order mutant now swaps the
`n_kv_heads` and `block_size` dimensions when allocating NumPy blocks. This
preserves the original layout pitfall against the pure-Python implementation.

## L8.3: no registered module calls the paged cache (verify check 9)

`ss verify course L8.3` fails check 9 by design, and no call site is faked.
The candidates were checked against the reference code:

- `L8.2` (`generate`) accepts the paged cache as a cache object, but `L8.3`
  depends on `L8.2`, so `L8.2` cannot list it in `deps` without a cycle.
- `L8.6` (speculative decoding) rolls rejected drafts back with
  `KVCache.truncate`. `PagedKVCache` has no truncate, and its fork shares
  blocks but cannot discard the verified tail, so using it there would mean a
  new API on `L8.3` and a rewrite of `speculative_generate` only to create a
  call.
- `L8.7` (constrained decoding) masks logits and keeps no KV state.
- `L9.4` (optional C paged attention) checks against fixture files that
  `L8.3` produced; it does not call the Python module.
- `L10.2` and `L10.4` reimplement block allocation and copy-on-write in Rust
  and list `L8.3` as reading.

The one runtime caller is the CLI entry layer (`ref/entry/python/tinyllm/
cli_infer.py`: `generate --cache paged`, adapted by `PagedHook`), which MS-L8
step 1 drives. The entry layer is not a registered module, so the mirror rule
cannot record it. Check 9 passes once a later Python module serves parallel
samples or beams from one prompt through `fork` (for example a
best-of-n generator, or GRPO rollouts in `L12.3` if they move from the Rust
engine to Python).
